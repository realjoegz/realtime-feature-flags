# Evidence

Each row states a claim and links the tests that prove it.

## 1. How the rows are checked

A Test cell links test files, with each test's full name, its `describe` titles and title joined by spaces, as the link text. `npm run verify` runs [`scripts/check-claims.mjs`](../scripts/check-claims.mjs) on every table with a Test column in README.md and this directory, and fails unless each linked test passed in this run's Vitest report. A failed, skipped, todo, renamed or missing test fails it, as do a file that failed to load, a link to a file, text outside the links, a row cut off by a blank line, and a report over 60 minutes old or older than a file under `packages`, `apps`, `tools`, `scripts` or `vitest.config.ts`. Its own tests cover each case. No test is retried.

A name ending in "(seed S, N runs)" runs fast-check with that seed, always 20261014, and that number of runs. `RFF_FC_SEED` and `RFF_FC_RUNS` change both, and the names with them, so only the committed runs pass the claim check.

## 2. The test setup

Vitest 5.0.4 runs one project per package, the API's compiled with SWC for Nest's decorator metadata. Each API test run, and each environment that writes tenant rows, gets its own database and Redis prefix on the compose servers ([`global-setup.ts`](../apps/api/test/harness/global-setup.ts)). Tests leave the shared roles rff_app and rff_owner unchanged and create tables only in scratch databases. Apps listen on free ports and are called with `fetch`, two per process in replica tests, and tokens come from key pairs made for the run ([`idp.ts`](../apps/api/test/support/idp.ts)). [`network.ts`](../apps/api/test/support/network.ts) cuts, stalls or redirects a client's connection, and [`bus-faults.ts`](../apps/api/test/support/bus-faults.ts) loses notifications, makes publishes throw and closes subscribers. SDK tests use a `fetch` they control ([`fake-stream.ts`](../packages/sdk/test/support/fake-stream.ts)), and dashboard tests run against a local OpenID provider that checks PKCE ([`provider.ts`](../apps/dashboard/test/support/provider.ts)) and a recording API ([`fake-api.ts`](../apps/dashboard/test/support/fake-api.ts)).

## 3. Rollout and evaluation

## 4. Tenant isolation in the tables

Checks run as `rff_app` in B's context and commit, then A's rows are compared by text and `xmin` on the superuser connection. The UPDATE sets a constant, or the identity columns to NULL, so only the policies decide its reach.
