# Evidence

Each row of the tables below states a claim and links the tests that prove it. Before each table, a few paragraphs say how its tests force their cases and which committed broken code they must catch. [Section 13](#13-latency) has the latency method and results, which are measured and not tested.

## 1. How the rows are checked

A Test cell links test files, with each test's full name as the link text: its `describe` titles and its own title, joined by spaces. `npm run verify` runs [`scripts/check-claims.mjs`](../scripts/check-claims.mjs) after the tests. It reads every Markdown table with a Test column in README.md and in this directory, and fails unless each linked test is in this run's Vitest report with the status passed. A failed, skipped, todo, renamed or missing test fails it, and so do a file that failed to load, a link that names a file instead of a test, text in a Test cell outside its links, a row that a blank line splits off its table, and a report that started more than 60 minutes ago or before a file under `packages`, `apps`, `tools` or `scripts`, or `vitest.config.ts`, last changed. Its own tests cover each of these. Vitest retries no test.

A test whose name ends in "(seed S, N runs)" runs fast-check with that seed and that number of runs. The seed is 20261014 in every property. `RFF_FC_SEED` and `RFF_FC_RUNS` change both for local exploration, and the test names change with them, so the claim check fails on such a run: a run that the tables count is always the committed one.

**What runs where.** CI runs two jobs on every push to `main` and every pull request ([`ci.yml`](../.github/workflows/ci.yml)): `verify` runs `npm run verify` against PostgreSQL and Redis from `compose.yaml`, and `local-stack` starts the whole stack with `docker compose up --build --detach --wait` and runs [`scripts/demo.sh`](../scripts/demo.sh). CI measures no latency; it checks only that the README table is the rendering of the committed results files.

## 2. The test setup

The tests run in Vitest 5.0.4, with one project per package. The API project compiles with SWC, which emits the decorator metadata that Nest's injection reads.

**Real PostgreSQL and Redis.** The API tests use the Postgres and Redis of `compose.yaml` on 127.0.0.1. Each test run creates a database of its own with the migration runner from `apps/api/migrations`, drops it at the end, and uses a Redis key and channel prefix of its own, so concurrent runs on one machine do not meet ([`global-setup.ts`](../apps/api/test/harness/global-setup.ts)). A test environment that writes tenant rows gets a migrated database of its own in the same way. The roles `rff_app` and `rff_owner` belong to the whole server, so no test changes them: a test that needs another role creates a scratch role, and a test that creates tables does so in a scratch database.

**Nest apps over HTTP.** A test app listens on 127.0.0.1 on a free port and is called with `fetch`, the stream included. The replica tests run two Nest apps in one process, on separate ports, on one database and one Redis prefix, as two replicas do.

**Tokens.** The API tests sign tokens with key pairs made for the run, whose key set the API fetches over HTTP from a local server ([`idp.ts`](../apps/api/test/support/idp.ts)), as it fetches Dex's. That allows tokens that Dex would never issue: expired, for another audience, signed by an unknown key, unsigned.

**Faults.** [`network.ts`](../apps/api/test/support/network.ts) sits between an SDK client and an app: it cuts a connection as a reset would, stalls it as a vanished peer would, so that only the client's read timeout notices, and sends the next connection to the other app. [`bus-faults.ts`](../apps/api/test/support/bus-faults.ts) loses a notification at one app's subscriber or at every app, makes a publish throw, and closes an app's subscriber connection with `CLIENT KILL`.

**Fakes outside the API.** The SDK client tests drive the client through a `fetch` that each test controls ([`fake-stream.ts`](../packages/sdk/test/support/fake-stream.ts)). The dashboard tests run its route handlers, cookie code, API client and server action in Vitest outside Next.js, against a local OpenID provider whose token endpoint checks the PKCE verifier as Dex does ([`provider.ts`](../apps/dashboard/test/support/provider.ts)) and a server that records the requests the API would get ([`fake-api.ts`](../apps/dashboard/test/support/fake-api.ts)). The latency tool tests run its code on values the tests make up, with a fake `fetch` and clock in place of the stack.

## 3. Rollout and evaluation

**How the properties are forced.** Each rollout property is a function of the evaluator under test. It must hold for `packages/core/src` and must be falsified, through `fc.check(...).failed`, for the committed broken evaluators aimed at it in [`packages/core/test/controls/`](../packages/core/test/controls/broken-evaluators.ts). Each of those is the real evaluator with one part replaced by a plausible bug, named in the row of the property it breaks. The scaffold they share, with no part replaced, passes every property, so each control differs from a correct evaluator in its one part. P1's second process is a child Node process that evaluates the same cases. P5's tolerance is 5 standard deviations of the binomial share, `sqrt(p(1 - p) / n)` for n = 100,000. P6's vectors come from the published answer the test file cites.

**The reference evaluator.** [`reference-evaluator.ts`](../packages/core/test/reference/reference-evaluator.ts) in the test tree shares no code with `src`, its MurmurHash3 and UTF-8 encoder included. The differential property draws attribute names and values from small shared pools, so rules match often and overlap. The pools hold near misses in case, surrounding spaces and Unicode normalization, and in three runs out of four the percentage sits at the user's bucket or next to it. Each of the four branches must be taken in at least 5 percent of the runs.

**The conformance file.** The reference evaluator writes [`evaluation-cases.json`](../packages/core/conformance/evaluation-cases.json) from seed 20261014, and a test generates it again and compares. The core tests and the SDK tests read it.

**Through the API.** The last row runs P2 against the running API: create a flag at p1, evaluate 25 users through `POST /evaluate`, PUT only the percentage to p2 >= p1, and evaluate again.

## 4. Tenant isolation in the tables

**The fixture.** [`fixture.ts`](../apps/api/test/isolation/fixture.ts) seeds tenants A and B with the same flag keys and different values, a unique canary string in every text and JSON column of A and none in B, a user who is owner in A and viewer in B, and a user in neither. A canary that turns up in B's context is a leak of A.

**The universe.** The detectors in [`detectors.ts`](../apps/api/test/isolation/detectors.ts) read from the catalogue every table, view, partition and sequence that `rff_app` holds any privilege on outside the system schemas, minus `public.schema_migrations`, and run each check on every one. A table that a later migration adds and grants `rff_app` any privilege on joins the universe by itself, and fails the precondition until the fixture gives it rows of A and of B and a canary in each text column.

**How the checks are forced.** The reads, writes and inserts run as `rff_app` in B's context, and the writes commit. A's rows are then compared by row text and `xmin` on the superuser connection, so a write that set a column to the value it had still shows. The UPDATE sets a constant and reads no column, so only the UPDATE policies decide which rows it reaches. The no-tenant check runs on a pool of one connection and checks that the backend pid is the same after A's transaction. The look-up functions are called under all 25 combinations of `app.tenant_id` and `app.user_id`.

**The controls.** The same detectors run against committed setups that leak, listed in the controls row below, among them look-up functions with one defect each from [`fixtures/isolation/`](../apps/api/test/fixtures/isolation/), and pass only when they report each one. The start-up check is run on scratch roles with each privilege.

## 10. Convergence and agreement

**Convergence.** [`simulation.ts`](../apps/api/test/support/simulation.ts) draws sequences of steps with fast-check and runs each on a new tenant with four SDK clients over `fetch`, two on each of two apps. A run's steps are a save through either app, 2 to 5 saves at once through both, dropping one client's connection by cutting or stalling it, reconnecting it, and moving it to the other app, which cuts its connection and waits until the other app answers its next one. Every fault is forced, not timed: a connection is cut or stalled by the client's own network, a notification is lost by the bus, a subscriber connection is closed by Redis. The 5 s deadline only stops a run that does not converge; the simulation makes no claim about how fast clients converge, and a separate row of section 9 bounds the poll's delivery time. In each configuration every kind of step and fault, saves that lost to a concurrent save, stalls that only a read timeout ended, and reconnections each occur at least 5 times, and every move ends on a connection answered by the other app. Three controls each remove two or all three of the paths that heal (the poll, the notifications and the read when a stream opens). A fourth reads the version and the flags 25 ms apart, so a snapshot can mix two versions.

**Agreement.** Both sides run `evaluate()` from `@rff/core`, so agreement proves the path the flags take (request bodies, Postgres, the Redis cache, JSON and the stream), and the conformance and differential rows of section 3 prove the evaluation. The controls break that path in three places: storage that loses the order of the rules, storage that returns the percentage as a string, and a second app that evaluates from a stale cache entry.

## 13. Latency

### The tool

`npm run latency -- --clients C --warmup W --changes M` ([`main.ts`](../tools/latency/src/main.ts)) runs against the compose stack. It signs alice, acme's owner, in through Dex with the curl code flow of `scripts/lib/dex-sign-in.sh`, opens C `FlagsClient`s from `@rff/sdk` with acme's demo SDK key, alternately on api-1 and api-2 and connected directly to their published ports, and waits until every client holds acme's current version. Then it saves W warm-up and M measured changes of the rollout of `dark-mode`, one at a time, each with a PUT to api-1. All times come from `performance.now()` in the one Node process that sends the saves and holds the clients:

- **t0** is read just before the PUT is sent.
- **The save round trip** ends when the PUT's response body has been read.
- **The time to the last client** runs from t0 to the latest of the clients' first `onChange` at the saved version or a later one.

The next change is sent only once every client holds the saved one, so changes never overlap. Before and after each phase the tool counts the clients' reconnects and reported errors, and the snapshots that the replicas logged as sent after a wake-up other than a Redis notification ([section 7 of the design](design.md#7-the-stream)). ### The runs

Two runs of `npm run latency -- --clients 100 --warmup 30 --changes 300` are committed, [`latency-20261014T170235Z.json`](../bench/results/latency-20261014T170235Z.json) and [`latency-20261014T170500Z.json`](../bench/results/latency-20261014T170500Z.json). The README table gives their results and the conditions both files record, at commit f64f196 with a clean tree. The commits after it change the docs, the results files, two test titles, a comment in the Dex configuration, the dashboard's sign-out route and its Next.js patch version, two lines of the demo's output and the CI checkout, and no code or configuration that a measured change passes through.

- **A few slow changes.** In each run 6 of the 300 measured changes took more than 10 ms to reach the last client.
- **Redis delivered every measured change.** Both runs had 0 reconnects, 0 client errors and 0 snapshots sent after a connect, ready or poll wake-up, in the warm-up and in the measured changes. With no reconnect, no stream opened during those changes, so each snapshot the clients applied for them came from a read that a notification asked for.
- **The warm-up is left out.** Its 30 changes per run are in the files with `"phase": "warmup"`; the slowest took 20.2 ms in the first run and 18.4 ms in the second.

### How far to trust this

- **One laptop, one process.** The clients ran in the Node process that sent the saves, on the host, and reached the replicas through Colima's port forwarding. No byte crossed a physical network, and the time to the last client includes that one process handling 100 streams on its event loop.
- **One tenant, one change at a time.** acme had 3 flags, and each change waited for the one before. The runs say nothing about concurrent saves, many tenants, large snapshots or thousands of streams.
- **300 samples per run.** The README table has no p99: with 300 samples a nearest-rank p99 is the fourth-largest value.
- **Two runs on one stack, minutes apart.** Their medians of the time to the last client differ by under 0.1 ms, their p95s by 1.2 ms and their maxima by 4.3 ms. Nothing here says how the numbers vary between machines or days.
